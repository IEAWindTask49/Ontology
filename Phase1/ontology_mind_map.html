How the ontology fits together

The file has three kinds of section, and they do three different jobs. Site describes the water, seabed and weather. Array-level says what exists, where it sits, and what connects to what. Component-level is a catalogue of unique designs, each written once no matter how many times it is used. Almost every line joining them is one of two things: a key reference by name, or a 1-based index into a list.

Site

Ambient conditions

Read by everything, referenced by nothing. No other section points at the site — the site constrains and feeds the models that consume the rest of the file.

answers: what is it like here?
Array-level

Instances & topology

Tables of placed objects. Each row has a unique ID and a set of coordinates; nearly every other column is a pointer into the component catalogue.

answers: what is where, joined to what?
Component-level

Design catalogue

One entry per unique design, with no absolute position. Two turbines sharing a hull cost one platform entry, referenced twice.

answers: what is each thing made of?

The two joints that hold it together

Names and indices

Two different pointer styles sit side by side, and mixing them up is the usual source of confusion.

By key — mooringID: ms3, cableType: static_cable_66, type: drag-embedment1. The value is a mapping key somewhere else in the file, or a name in an external library.

By index — topsideID, platformID, fairlead, JTubeA. The value is a position in a list, counting from 1, with 0 reserved to mean “none” for topsides and platforms.

Headings compose

No mooring or cable heading in this file is a compass bearing on its own. Each one is relative, and they stack:

array.heading_adjust rotates the platform; the heading in mooring_systems or array_cables is then measured from that rotated platform, clockwise from north.

That is exactly what makes ms3 reusable — the sample points FOWT1 at 180° and FOWT2 at 0°, and one mooring system serves both.

Fairleads and J-tubes expand

Inside platforms, a fairlead entry with headings: [30, 150, 270, 35] is not one point — it is four, and they take indices 1 to 4 in the order written. A second named entry continues the count.

Those numbers are what mooring_systems.fairlead, array_mooring.fairleadA/B and the JTube keys are pointing at. A list instead of a single value means a bridle: one line meeting the hull at several points.

one line through the file
array row FOWT1 → platformID 1 → platforms[1] → fairleads, headings 30/150/270/35
    ↳ mooringID ms3 → mooring_systems.ms3 → 3 × semitaut-poly_1 at fairleads 1, 2, 3
        ↳ mooring_line_configs.semitaut-poly_1 → chain ⌀0.1549 × 477.7 m + polyester ⌀0.182 × 199.8 m
        ↳ anchorType drag-embedment1 → anchor_types → DEA, zlug 10 m → soil under that x,y from site.seabed

Things worth knowing about the sample

  1. Not every reference resolves inside the file. The sample has no cable_types and no mooring_line_types section, yet it names dynamic_cable_66, static_cable_66 and the chain/polyester families. Those are looked up in the FAD-Toolset cableProps_default.yaml and MoorPy's mooring property scaling. Absence is a fallback, not an omission.

  2. Column order is declared, not fixed. The sample and the template write array_cables as … DynCableB, JTubeA, JTubeB, headingA, headingB, cableType; the README example puts the headings before the J-tubes and spells them JtubeA. Because every table carries its own keys row, both are valid — always read the keys, never assume the order.

  3. RAFT_cases, RAFT_settings and marine_growth live under site. The README shows them as unindented code blocks, which reads as top-level. OntologyTemplate.yaml settles it: all three are nested inside site:.

  4. The DEA in the sample uses different keys than the README documents. drag-embedment1 is given B: 5 and L: 2; the README's DEA template asks for A, the net fluke area, plus zlug. Worth confirming which the anchor capacity model actually reads.

  5. Appendage keys differ between the sample and the README. The sample writes m, l and volume on buoyancy_module_1; the README example writes mass, length and volume. Both appear in circulation.

  6. The fourth fairlead heading is unused. The platform defines headings [30, 150, 270, 35], giving four indices, but ms3 only references 1, 2 and 3. Index 4 sits at 35°, ten degrees off the first — likely a leftover, and a good reminder that the fairlead list is positional.

  7. Both cable sections are populated. array_cables carries the suspended FOWT2 ↔ OSS1 link, while cables carries array_cable1 from FOWT1 to FOWT2 with routing vertices and a burial profile. They are alternatives per cable, not per file.
